`docs/design-row-representation.md` (landed 2026-06) ranks architectural options for the whole-row-hashing CPU bottleneck (see [[parallel-pipeline-perf]]). Researched how Differential Dataflow (arrangements) and Feldera/DBSP (Ord columnar batches in an LSM spine) represent/share indexed state.

Key reframes vs. the old roadmap assumptions:
- **We already built the arrangement substrate**: the `Spine*` trace family is sorted-columnar immutable LSM batches (`TKey[]/offsets/TValue[]/TWeight[]`, bloom, spill). But it's opt-in (`TraceFamily.Flat` is default), persistence-oriented, **per-operator with zero sharing**, and its operators still **point-probe** (`GroupFor(key)` per delta key) instead of merging. So the gap is the **execution model + sharing**, not the storage format.
- **Demoted "integer surrogate keys" (the old top pick)**: neither DD nor Feldera interns rows to ints; interning re-introduces a boundary hash, only amortizes for low-card keys not wide fact rows, and is a W>1 contention hazard. Salvageable only as a narrow per-column key dictionary.
- **Demoted whole-query codegen**: Feldera abandoned monomorphization (compile-time) and stayed fast → dispatch is not the lever; our profiling already showed hashing, not dispatch, binds.

Recommendation/ranking: (1) ⭐ **merge/columnar execution on the spine** — galloping search for tiny deltas (compare key, not hash row), cursor merge for big deltas; highest ROI, substrate exists; (2) shared arrangements (TraceHandle/import + arrangement CSE), query-dependent; (3) per-column key dictionary; (4) typed ingest (cheap, do alongside); (5) codegen, (6) global interning — deferred.

Incremental caveat the prototype must settle (§5): tiny per-tick deltas vs huge state mean full merge is O(state) — worse than probe; galloping is the right primitive at delta=1, merge only wins with larger batches. `PureTraceBenchmark` (delta sweep) + `nexprofile` (q4 step) are the gate. First increment = convert the q4 `SpineIncrementalAggregateOp`/join probe to merge/gallop, ship only if it beats flat at W=14 without regressing delta=1.

**Prototype DONE (uncommitted, on main working tree as of 2026-06-08):** added `SortedKeySearch.GallopIndexOf` (cursored exponential search, int/long specialized) + `SpineIndexedZSetTrace.GroupForManySorted` (batched merge probe: sorted delta keys galloped against each sorted batch once, matched groups sliced from value columns with NO ZSet rehash). New `MergeProbeBenchmark` + `dotnet run -- mergeprobe` subcommand → results in `docs/merge-probe-bench.md`. 5 new PBT/unit tests (all green; benchmark also self-verifies vs GroupFor). **Result: hypothesis confirmed — merge beats point-probe 2–135×, growing with tick width D and (for misses) state size; only soft spot is literal D=1 at mid N (0.17–0.34×), guardable with a one-line size check.** Absent-key (join probe-side) wins biggest (135× at N=1M,D=4096). Next: wire GroupForManySorted into `SpineIncrementalAggregateOp.Step` + spine join, measure end-to-end on q4; the one open question is feeding the aggregator sorted runs without rebuilding a ZSet (watch [[typed-compiler-reflection-gotcha]]).

Remaining deferred: end-to-end q4-on-spine W=14 (parallel harness flat-only → rollout step), spine LEFT/FULL joins, flipping TraceFamily.Spine toward typed default.

**Join merge-probe LANDED (2026-06-08, committed).** Wired `GroupForManySorted` into `SpineIncrementalJoinOp.Step` (both passes): sort each delta side's keys once, batched gallop-merge probe instead of per-key `GroupFor`, matched sorted runs feed the unchanged cross-product; `D==1` keeps the point probe. Correctness verified (full spine join suite + spine-compile + random-query PBTs green). **Did the JOIN first, inverting the design doc's order (which scoped the aggregate first) — because on reading the code the join is the CLEAN consumer (pure cross-product iteration, no aggregator interface) and the aggregate is the HARD one.** Key finding that demotes §8's Option D for the aggregate: the **typed** SQL aggregators (`TypedSqlAggregators.cs`, the path q4 uses) are already incremental and consume `afterMultiset` by **point-probe** (`after.WeightOf(deltaRow)`) + a `SumWeights()` gate, NOT a full scan — so feeding them a sorted span to scan (Option D) doesn't fit; the aggregate win really needs **Option B** (an `IMultiset` abstraction so `after` answers WeightOf/SumWeights/enumerate off a sorted run without hashing). Structural Sum/MinMax DO scan, so D fits the structural path only. Operator-level gate (`docs/join-probe-bench.md`, `dotnet run -- joinprobe`, seam = `SpineJoinProbeMode.ForcePointProbe`): **1.2–2.8× faster Step on multi-key ticks, no D==1 regression** (smaller than trace-level 2–135× because Step also pays the unchanged cross-product/build/integrate). Deferred: end-to-end q4-on-spine W=14 (parallel Nexmark harness compiles flat-only — belongs with the "flip TraceFamily.Spine toward typed default" rollout); spine LEFT/FULL joins (same drop-in); the aggregate (needs the Option B reckoning above).

**q4 END-TO-END GATE RAN — spine loses to flat, do NOT flip the default (2026-06-08).** Built `Q4SpineBenchmark` + `dotnet run -- q4spine [events] [W] [runs]` (report `docs/q4-spine-bench.md`, design doc §8.3): compiles q4's WHOLE parallel pipeline three ways at host cores, times **step** apart from split/gather, cross-checks every config vs flat. Three-way A/B = **flat** / **spine·point** (`ForcePointProbe` both ops = LSM substrate w/o merge) / **spine·merge** — this separates the substrate cost from the probe win that a bare spine-vs-flat number conflates. **Result (W=24, 1M events, median-of-3, stable across 2 runs):** at batch 10k flat≈675ms vs spine·merge≈1650ms (**0.40×**); at batch 100k flat≈675 vs spine·merge≈955 (**0.68×**). Verdict, cleanly split: (1) **merge probe CONFIRMED end-to-end** — spine·merge beats spine·point 1.04× (10k) / 1.11× (100k), reproducing the joinprobe/aggprobe microbench direction in the real pipeline; (2) **but the spine SUBSTRATE loses to the flat dict 1.4–2.5×** — the gap is all spine·point, not the probe. Cause is structural & matches §5: at W=24 each replica's tick delta is batch/24 rows → spine rebuilds many TINY sorted batches/tick (build+bloom+compaction) where flat does in-place hash updates; merge makes it cheaper, can't erase it. Gap narrows as batch widens (0.41×→0.68×) but never crosses 1.0× at realistic q4 ticks. **Consequence:** ship condition ("beats flat at W=14") NOT met → keep `TraceFamily.Flat` default; the merge probe stays committed (behind D==1 guard) as the execution model. **The bottleneck is no longer the probe (Option 1 done+validated) — it's the per-operator zero-sharing substrate cost. Next increment = Option 2 / shared arrangements (§6.2): build the indexed batch once, share across operators / amortize across ticks.**

**Option 2 increment 1 LANDED — cross-operator shared arrangements, FLAT (2026-06-08, design doc §9).** Built the read-only sharing handle + a join that reads it, exactly §6.2's scoped first increment (before compaction coordination), on the flat substrate first (simpler, family-agnostic, apples-to-apples with the q4-winning substrate). New: `IArrangement<TKey,TValue,TWeight>` (Current = after-trace) + `ArrangeOp` (integrates one indexed delta stream into ONE IndexedZSetTrace, exposes the handle; registered before consumers so they read the post-delta integral same tick) + `IncrementalJoinSharedRightOp` (RIGHT side = shared IArrangement, owns only the left/delayed trace) in `Operators/Stateful/Arrangement.cs` + `IncrementalJoinSharedRightOp.cs`; factored the join cross-product into shared `IncrementalJoinCore.JoinInto` (used by both the private-trace and shared joins — no behaviour change, full suite green). Builder API (internal): `Arrange(indexedStream)` + `IncrementalInnerJoinSharedRight(...)`. **Key feasibility insight: sharing needs NO change to the join math** — both `A⋈R` and `B⋈R` want `R_t`(after)+`dR`; the arrangement folds dR once, both read it, each keeps its own left trace; the after-side asymmetry is always satisfiable (inner join commutes). Verified: `SharedArrangementTests` (same-tick / late-right / retraction / 4 seeded random sequences) asserts byte-identical output shared-vs-unshared; 1648 suite pass. Gate (`dotnet run -- sharedarr`, `docs/shared-arrangement-bench.md`): **sharing wins across the grid (every cell ≥1.0×), grows with fan-out F — ~1.0–1.3× at F=2, ~1.2–1.4× at F=4, ~1.5× at F=8** (clearest at D≈1024; ~±0.2× cell jitter; D=4096 noisiest as per-step alloc dominates). Ceiling modest because the flat integrate it dedups is a cheap in-place dict merge. **Two follow-ups carry the real prize: (1) SPINE arrangement** — there the duplicated per-consumer maintenance is the expensive sorted-batch build (+bloom+compaction = the §8.3 q4 bottleneck), so sharing should pay much more; variant = spine `Arrange` whose consumers probe via `GroupForManySorted` against the shared trace, reusing this same IArrangement; **(2) arrangement-CSE optimizer rule** — today only reachable via the Core builder, no SQL routes through it; rule detects a relation arranged by same key for ≥2 ops (star-schema/self-join/repeated-CTE, reduce-by-K→join-on-K), gate = synthetic star-schema (q4 has no reuse). Also deferred: coordinated GC on the shared trace (DD's compaction sharp edge).

**Option 2 increment 2 LANDED — SPINE arrangement; hypothesis REFUTED (2026-06-09, design doc §9.5).** Built the spine counterpart of the flat shared arrangement: `ISpineArrangement<TKey,TValue,TWeight>` exposes the `SpineIndexedZSetTrace` ITSELF + key comparer (NOT a materialized Current — consumers probe via `GroupForManySorted`, never materializing the integral) + `SpineArrangeOp` + `SpineIncrementalJoinSharedRightOp` (probes shared trace for R_t, owns only delayed left trace); extracted `SpineJoinProbe` static helper (ProbeAndJoin+SortedKeysOf) shared by the private-trace `SpineIncrementalJoinOp` and the shared op (no behaviour change, D==1/ForcePointProbe seam kept). Builder API (internal): `SpineArrange` + `SpineIncrementalInnerJoinSharedRight`. `SharedArrangementTests` parameterized over BOTH substrates (14 cases green, suite 1655). **KEY FINDING — the §8.3 expectation that "spine sharing pays much more" is WRONG: spine sharing is real & correct but its ratio is COMPARABLE TO / slightly BELOW flat (both ~1.0–1.1× at F=2 → ~1.2–1.4× at F=8).** Why: sharing removes a relation's per-tick MAINTENANCE (integrate), which is NOT the dominant per-tick term — the per-consumer PROBE of R_t (each join probes with its own left delta) + cross-product + output + left-integrate stay per-consumer/unshared; and spine's heavier GroupForManySorted probe inflates its baseline ~1.5–2× vs flat, so the similar ABSOLUTE saving is a SMALLER FRACTION → diluted ratio. **Honest correction to §8.3: it conflated two levers — the spine substrate's q4 loss is per-tick REBUILD paid even WITHOUT reuse (cross-tick/amortization), whereas arrangement sharing is CROSS-OPERATOR and only fires when a relation is arranged by the same key for ≥2 consumers, which q4 DOESN'T have (§6.2).** So cross-operator sharing = a modest, broad-surface, fan-out-scaling win for star-schema/self-join/repeated-CTE shapes, NOT the lever that flips spine past flat on q4. Abstraction now complete+correct on both substrates; **sole remaining follow-up = arrangement-CSE optimizer rule** (detect same-relation-same-key ≥2 consumers → one Arrange) so SQL routes through it (today Core-builder-only). GC coordination on shared traces still deferred. Closing the spine q4 gap is a DIFFERENT problem (cross-tick rebuild amortization / bigger ticks per replica), not sharing.

**Option 2 increment 3 LANDED — arrangement-CSE optimizer rule (2026-06-09, design doc §9.6).** Makes cross-operator sharing reachable from SQL. Opt-in `CompileOptions.ShareArrangements`. **Implemented as compile-time CSE in the structural PlanToCircuit, NOT a PlanOptimizer tree rewrite** — because the logical plan is a TREE but sharing is a DAG (one arrangement, ≥2 consumers). Key enabler: the compiler ALREADY compiles a base-table scan / repeated CTE ref to ONE shared Stream (`CompileContext.Scans`/`CteCache`), so "same relation" identity is free. Mechanism: pre-pass `CollectShareableArrangements` (mirrors `CollectScans`) counts inner-join right inputs by `ArrangementKey(source, rightKeySig)` where source = CteRef (ref-identity) or table name (value-identity); marks count≥2; only bare ScanPlan/CteScanPlan right inputs (+ non-AllowNullKeys joins) qualify. `CompileInnerJoin` consults per-compile `ArrangementCache`: first qualifying join builds right-index+Arrange/SpineArrange, rest reuse; shared relation = R_t (after) side so output byte-identical. Added `EmitSharedRightInnerJoin` (flat/spine dispatch) + `Compile(plan, CompileOptions, IRowCodec)` overload (params reordered options-before-codec to avoid CS0121 ambiguity with `Compile(plan, ISqlSnapshotCodecs?, CompileOptions?)`). **Guards: engages only when no join-key GC frontier AND no snapshot codec (shared ops carry neither yet); flag also FORCES structural path (CSE structural-only, skips typed fast path).** Verified: `ArrangementSharingTests` — rule fires (exactly 1 Arrange/SpineArrange + 2 shared joins for 2-fact star schema), doesn't fire w/o reuse, identical results to unshared over random insert/delete on flat+spine; suite 1660. Gate (`dotnet run -- sharedarrsql`, `docs/shared-arrangement-sql-bench.md`): wide dim joined by F facts, structural-shared vs structural-unshared (same codec) → **SQL-level win only ~1–6% (grows with F), smaller than operator-level ~1.5%** because at query level the dedup'd dim maintenance is a tiny fraction of per-step work (input encoding/per-fact reindex/UNION/projection/output all unchanged). **Test-bug lesson: when A/Bing two circuits, generate the random delta sequence ONCE and apply to BOTH — advancing the same rng separately per circuit feeds them different inputs (false mismatch).** Deferred: typed-path CSE (flag forces structural today); left-side sharing (commute joins so shared rel is on after side); general subplan fingerprinting beyond bare scans/CTE refs; coordinated GC/snapshot for shared traces. **Option 2 now COMPLETE: abstraction (flat+spine) + reachable from SQL; the realistic payoff is a modest broad-surface fan-out-scaling win, NOT the lever that flips spine past flat on q4 (that's the separate cross-tick rebuild-amortization problem).**

**Cross-tick spine amortization LANDED — the memtable; CLOSES the §8.3 q4 gap (2026-06-09, design doc §10).** THE big one: makes the spine substrate competitive with flat on q4, the blocker §8.3/§9.5 flagged. §8.3's gap = per-tick REBUILD paid even with no reuse (at W=24 each replica's tick delta = batch/24 → spine builds many tiny sorted batches/tick where flat does in-place dict updates) — a CROSS-TICK problem; classic LSM fix = a memtable. Added a mutable in-memory memtable (`IndexedZSet`) to `SpineIndexedZSetTrace`: when enabled, `Integrate` folds delta in-place (flat cost) and flushes to ONE sorted batch only at ≥N distinct keys (amortizes build+bloom+compaction across N keys' worth of ticks). ALL reads (GroupFor, GroupForManySorted, MaterialiseGroups→Materialize/Entries/GroupCount, IsEmpty), GC (DropKeysBelow), snapshot (GetBatches flushes first) merge memtable+batches; weights sum (Z-set add commutes → memtable is just another additive layer). **Opt-in via static seam `SpineStagingConfig.Capacity` (default 0=disabled), mirroring SpineJoinProbeMode.ForcePointProbe — trace reads it once at construction → NO operator/builder signature change (dodges typed-compiler reflection gotcha) + NO wide plumbing. At 0 the memtable is never populated and `!_memtable.IsEmpty` guards short-circuit → byte-identical to before, so all ~13 batch/level-structure assertions + 4 flat-vs-spine PBTs pass untouched.** Verified: new `SpineMemtableTests` (caps 1/4/16/64 match flat oracle on GroupFor+GroupForManySorted+Materialize read EVERY tick mid-stream before flush, + memtable-only-key/flush-on-snapshot/GC-from-memtable/intra-memtable-cancellation); suite 1668; q4 gate end-to-end output cross-check passed with staging on the real parallel pipeline. **Gate (`q4spine`, added spine·point·staged + spine·merge·staged configs, StagingCapacity=8192): staging CLOSES the §8.3 gap — at batch 10k spine goes from 0.47–0.66× (point) / 0.53–0.92× (merge) to ~0.8–1.2× (roughly DOUBLES spine step throughput); at batch 100k reaches parity ~1.0–1.03×.** Noisy parallel bench straddles 1.0× at 10k (run1: 1.10–1.23×, run2: 0.79–0.84×) → honest claim = gap closed / parity, not guaranteed win. Findings: (1) staged·point ≈ staged·merge — once memtable absorbs recent deltas at tiny D, merge probe adds little over dict point-probe (§5 D==1 caveat); the MEMTABLE not the probe is what matters here; (2) staging helps MOST at small batches (tiny ticks where per-tick build dominated), least at large (build already amortized) — inverse of the merge-probe curve. Default-off; flipping TraceFamily.Spine+capacity toward default = follow-up gated on fuller eval (1M, more runs/queries, capacity tuning). Memtable is on SpineIndexedZSetTrace (join+aggregate+shared arrangements); SpineZSetTrace (DISTINCT/import) deferred.

**Spine aggregate read path CLOSED q4's residual gap — the lazy merge-view (2026-06-09, design doc §12).** q4's inner MAX(price) compiles to `TypedSqlMinMaxAggregator` which is INCREMENTAL: per tick it probes only the few DELTA rows via `after.WeightOf(row)` + maintains its own SortedSet — NOT a full scan. But `SpineIncrementalAggregateOp` materialized the WHOLE after-group every tick to serve those few probes: GroupForManySorted gathers the before-run (O(N)) THEN MergeDeltaIntoRun merged it with delta into a fresh sorted array (another O(N)+alloc), just so WeightOf could binary-search it; flat answers O(1) from its dict. That redundant O(N) merge was the spine's drag on q4's growing per-auction groups w/ small deltas. **FIX = `MergeViewMultiset<T>`** (new, Spine folder): lazy IMultiset view over (beforeRun, groupDelta) — WeightOf = binary-search beforeRun + O(1) delta lookup (probe-only ticks pay NO merge); IsEmpty short-circuits O(1) for non-empty/growing groups (first beforeRun value the delta doesn't touch has net=beforeW≠0; beforeRun is zero-free); SumWeights = sum(beforeRun)+delta.SumWeights() (no merge); enumerate (SUM/COUNT/AVG + non-incremental MIN/MAX Compute) folds lazily = old eager-merge cost minus the throwaway array. Enumeration NOT sorted — sound bc all IMultiset consumers fold commutatively. Op merge path now hands MergeViewMultiset instead of SortedRunMultiset(MergeDeltaIntoRun(...)); removed MergeDeltaIntoRun + _runComparison field. SortedRunMultiset now production-dead (only comments ref it; no CA1812 → harmless, kept). Verified: full suite 1672 (existing flat-vs-spine SUM/MIN PBTs + SQL random-query PBTs exercise it); aggprobe merge-vs-point still 1.5–4.3×. **Result (q4spine batch 10k, 3 runs): q4 spine·merge·staged vs flat = 0.99×/1.11×/1.20× = PARITY-TO-AHEAD, up from §11's 0.92×; and merge·staged now beats point·staged (merge-view made merge the winning probe). Within ±0.1× parallel-bench noise but gap CLOSED → all 3 stateful Nexmark queries (q3,q4,q9) now parity-or-better with spine+memtable.** Removes §11's q4 objection; global default stays Flat (stateless/join-light gain nothing). **Deferred deeper idea: for probe-only aggregators skip even the O(N) GroupForManySorted gather, probe individual delta values across batches (WeightOfValueInGroup) — blocked on a cheap per-group emptiness signal (IsEmpty needs beforeRun today); not needed to reach parity.** Also still deferred: SpineZSetTrace (DISTINCT/import) memtable.

**Memtable for the NON-INDEXED trace LANDED — DISTINCT + import (2026-06-09, design doc §13). LAST deferred row-rep item.** Applied the §10 memtable to `SpineZSetTrace` (backs SpineDistinctOp + SpineImportTrace/recursive-CTE import state) — identical pattern to SpineIndexedZSetTrace but over a mutable `ZSet` instead of IndexedZSet: Integrate folds delta in-place (flat cost) + flushes to one sorted batch at ≥capacity keys; all reads (WeightOf, MergeEntries→Materialize/Entries/KeyCount, IsEmpty), GC (DropKeysBelow), snapshot (GetBatches flushes first) merge memtable+batches.
