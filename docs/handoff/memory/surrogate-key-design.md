Started 2026-06-09. Direction chosen by the user for the row-rep follow-up: **a design doc + benchmarked prototype of integer surrogate keys / dictionary-encoded rows** so exchanges/joins/aggregates hash ints, not whole row structs. Framed as the strategic #1 lever — "biggest ROI, would lift nearly every query's scaling — design-first and multi-session."

This deliberately **revisits the demotion in [[row-representation-design]] §6.5/Option 6**, which argued global row interning (a) re-introduces a boundary hash, (b) only amortizes for low-card keys not wide near-unique fact rows, (c) is a W>1 contention hazard, (d) breaks hash-partition routing, (e) is done by neither DD nor Feldera. The design must honestly re-litigate those against the CURRENT code, not hand-wave.

Key facts already verified this session about the **flat default path** (what Nexmark-vs-Feldera measures):
- Exchange **routing hash is already narrow** — `ExchangeIndexOp._partition` hashes `keyOf(row)` (the bigint key), NOT the whole row. The "exchange hashes the full row" claim in design §1 is STALE (ExchangeIndex fusion fixed it).
- Residual whole-row hashing on flat path is in the **inner value multisets**: exchange-gather builds `IndexedZSet` inner keyed by full row; aggregate `beforeGroup+groupDelta` rebuild re-hashes all value rows in a group **every tick the group changes** (q4 per-auction groups GROW → same rows re-hashed across many ticks — this is where §6.5's "only wins if row recurs" condition IS actually met); join cross-product; output build.
- The spine merge/merge-view work (§12) already killed the aggregate re-hash on the SPINE path, but flat still rebuilds.

The whole spine arc (design §5–§13) is DONE and concluded flat stays default — so it did NOT move the flat-path Nexmark numbers. This surrogate-key lever is the first thing aimed squarely at the flat default path.

**DESIGN DOC WRITTEN — `docs/design-row-representation.md` §14 (2026-06-09, design-first, NO code yet).** The deliverable for this session. Key argument (the reframe that justifies re-opening §6.5's demotion): the spine arc (§5–§13) empirically proved **flat-dictionary execution beats sorted-merge on our fine-grained ticks** (§8.3 spine loses 1.4–2.5×; memtable §10–13 only reaches parity, and the memtable IS a flat dict). §6.5 demoted surrogates because the doc's thesis was to adopt DD/Feldera sorted key-compare (which makes interning redundant). That thesis lost. In a flat-dict-wins world, the dict's one remaining cost is that **its keys are whole rows** → surrogates (intern row→int, hash ints) become the live lever — the synthesis DD/Feldera don't need and we do.

The §6.5 objection I REFUTED with code: §6.5 said interning wide near-unique fact rows saves nothing ("hashed once"). FALSE on the hot path — `IncrementalAggregateOp.cs:126` `afterGroup = beforeGroup + groupDelta` re-hashes the ENTIRE inner Z-set every tick a group is touched (unconditional, for Update + IsEmpty gate). A growing group (q4 per-auction bids) → O(K²) whole-row hashes. **Incremental maintenance CREATES the row recurrence §6.5 assumed didn't exist.** Surrogate it once → K struct-hashes + O(K²) int-hashes.

Design decisions in §14: surrogates are **operator-local + reversible** (Dictionary<TValue,int> forward + List<TValue> reverse), applied to STATEFUL ops only (win needs re-touch>1× to amortize intern; stateless map/filter would LOSE). Locality defuses §6.5(c) W>1 contention (post-exchange rows already co-located per worker, no global table); routing already narrow so §6.5(d) moot; surrogates never persisted (deref at snapshot codec boundary) so no codec problem. Reversibility mandatory: MIN/MAX compare VALUES not surrogates → deref to compare (O(1) list read, cheaper than struct rehash). GC reclamation deferred (prototype leaks).

**The honest control §14 insists on: flat lazy merge-view** (port §12's MergeViewMultiset to flat) kills the line-126 O(K²) rebuild WITHOUT surrogate machinery — aggregate-only, smaller, lower-risk. Surrogates must beat the lazy-view control on q4 AND win on join-heavy q3/q9 (where there's no single group rebuild to elide) to justify themselves.

**MICROBENCH RAN — design §14.9, DECISION: build the lazy view, NOT surrogates (2026-06-09, committed-pending).** Built `SurrogateKeyBenchmark` + `dotnet run -- surrogatebench` (report `docs/surrogate-key-bench.md`; wired into Program.cs; build 0 warnings). A/Bs whole-row-keyed Dictionary vs interned-int-keyed (surrogate total INCLUDES one-time intern) across row width (W2/W4/W8 longs, WStr=bid-like 3 longs+string) × re-touch R, faithfully modeling the verified `ZSetBuilder.From` per-entry re-hash (`ZSetBuilder.cs:91-94` does `d[k]=w` per entry — genuine re-hash, NOT bucket-copy; confirms §14.2 O(K²)).

**Bug I caught + fixed mid-run:** first `SurrogateGrow` did `d[forward[rows[i]]]` in the rebuild loop = re-hashed the STRUCT every rebuild (the cost surrogates remove) → growing-group falsely LOST <1.0×. Real surrogate op stores ids (`ZSet<int>`); fixed to store `int[] ids` + rebuild from ids → flipped to winning. Lesson: model the surrogate inner multiset as ids, never re-look-up by struct key.

**Results (clean, 21 samples, GC.Collect between cells):** (1) crossover R\*≈2–4 for rows wider than 2 longs; growing-group (q4 per-auction shape) WStr 1.4× at K=16 → **5.3× at K=1024**, W8 3.7×, even W2 1.05–1.4×. Headline: at K=1024 surrogate rebuild ~2.3–2.5ms REGARDLESS of width (struct 3.0→13.1ms) = surrogates make rebuild cost WIDTH-INDEPENDENT. (2) **The R=1 column is the killer: surrogates LOSE at R=1 (0.70–1.05×)** — pure intern overhead, the §14.3(a) loss regime, MEASURED.

**The decisive synthesis (§14.9):** inventory every whole-row-hash site by re-touch R → the ONLY R≫1 site in the whole engine is the **aggregate group rebuild** (O(K)). Exchange-gather/join-integrate/output-build are all R=1 (surrogates lose); join cross-product enumerates (no re-hash). And the **flat lazy merge-view** (the §14.5 control) REMOVES the aggregate rebuild (O(K²)→O(K), probe delta vs before-ZSet, never materialize afterGroup) → asymptotically beats the surrogate-rebuild on the one site that matters. So surrogates are DOMINATED: lose at every R=1 site, beaten by the lazy view at the one R≫1 site. Lazy view is also CHEAP (§8.2 IMultiset widening already lets Update take a non-ZSet; §12 MergeViewMultiset is the spine precedent → flat analogue over (beforeZSet, groupDelta), no intern/reversibility/GC/locality machinery).

**DECISION:** (1) build + benchmark the **flat lazy merge-view** as the real aggregate lever; (2) do NOT build operator-local surrogates; (3) global/cross-operator interning stays demoted (§6.5) — the only surrogate form that wins broadly is sharing one space across an op chain (per-op R=1 → pipeline R=#ops), which IS §6.5's global-interning with all its W>1/boundary-hash/routing hazards; R=1 loss reinforces the demotion. The §14.6 gate did its job: measure-first retired an XL option before any op wiring.

**FLAT LAZY MERGE-VIEW LANDED + pushed (design §14.10, commits f79a20b microbench + 3df999e the view).** Built `LazyMergeMultiset<T>` (`Operators/Stateful/LazyMergeMultiset.cs`) — flat analogue of §12's spine MergeViewMultiset, SIMPLER (flat before-group is a hashed ZSet with O(1) WeightOf/Contains → NO binary search). `IncrementalAggregateOp` now hands the aggregator this lazy view over (beforeGroup, groupDelta) instead of materializing `beforeGroup + groupDelta`. Default ON; eager rebuild kept behind seam `FlatAggregateMode.ForceEagerRebuild` (process-global bool, mirrors SpineAggregateProbeMode); per-key body factored into `EmitForKey`. NO builder-sig change (the op already takes IMultiset after the §8.2 widening) → reflection-safe; typed q4 path reaches it (TypedPlanCompiler line 2609 InvokeIncrementalAggregate → same op w/ typed TValue).

**Correctness:** LazyMergeMultiset.IsEmpty == eager (before+delta).IsEmpty (ZSetBuilder drops zero-net entries → dict-shape emptiness IS "all cancel"; O(1) for growing groups). FULL SUITE GREEN 1743 passed 0 failed. CA1859 forced a SuppressMessage on EmitForKey (afterGroup genuinely polymorphic: ZSet eager vs LazyMergeMultiset lazy).

**Gate (`dotnet run -- flatagg`, docs/flat-agg-bench.md, q4 MAX-over-growing-groups shape, outputs cross-checked identical): lazy beats eager 4.6–19×, GROWING with K** (K=128 8.6×, K=512 4.6×, K=2048 19.3×; eager 13.8s vs lazy 0.7s at K=2048). **Two regimes (verified by reading MinMaxAggregator.cs):** structural MinMax SCANS (Compute-only, inherits Update=>Compute) → lazy gives CONSTANT-factor win (removes per-tick dict alloc + wide-row rehash, leaves the scan); INCREMENTAL aggregators (SUM/COUNT/AVG + q4's TYPED MinMax which probes delta) → lazy gives full ASYMPTOTIC O(K²)→O(K). Harness gotcha fixed: `acc += q.Current` cross-check accumulation is itself O(K²) → moved OUT of the timed loop (was inflating lazy).

**END-TO-END q4 GATE DONE + pushed (design §14.10, commit 7b3157d).** Added `ForceEagerRebuild` knob to `SpineParallelHarness.RunConfig` (sets FlatAggregateMode seam alongside the probe modes; +`FlatEager` helper) + `Q4FlatBenchmark` (`dotnet run -- q4flat [events] [W] [runs]`, report docs/q4-flat-bench.md): whole q4 W-replica parallel pipeline flat·eager vs flat·lazy, step timed apart from split/gather, lazy output cross-checked identical. **Result (W=24, 1M events): operator-level 4.6–19× dilutes to ~1.3–1.5× QUERY-LEVEL step win on q4** (10k batch 1.28–1.55× across runs; 100k 1.48× at runs=5). Meaningful — q4 is the worst non-inherent Feldera gap (0.53×) and is step-bound on this aggregate. **NOISE: the 100k batch = ~10 Step calls/pass → one single pass read 0.83× before settling ~1.5× at runs=5; trust small-batch + multi-run medians.** Lazy only ever removes the rebuild → NO regression regime; variance is measurement.

**ROW-REP FLAT-PATH ARC COMPLETE.** Surrogate keys = CLOSED (dominated, §14.9: win only at R≫1, sole such site is the agg rebuild which the lazy view removes; R=1 sites lose; global interning stays demoted). The flat lazy merge-view is the SHIPPED lever (operator 4.6–19×, query ~1.3–1.5× on q4). All on main. Possible future (not scoped): the same lazy-view idea anywhere else with a per-tick rebuild; revisit surrogates only if a cross-operator-sharing design emerges that beats the R=1 per-op loss.
