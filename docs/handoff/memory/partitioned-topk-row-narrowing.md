Design arc §22 (design-row-representation.md) — measure-first session on the last competitive Nexmark gaps q18 (0.34× single-core) / q19 (0.32×), both partitioned TOP-K on `PartitionedTopKOp`, both `SELECT *` (NOT column-prunable, so §21's lever doesn't transfer). **Design-only, no operator code shipped.**

**Decomposition (durable):** combined `stepprofile` + extended `q18profile` (now q18+q19, reframed as the egest/phase-d probe). Phase (d) out-of-Step output ≈0% (egest 0–1%). Single-core both 100% in-Step TOP-K op. At W=10: q18 = 43% exchange-move + 35% op + 22% wait; q19 = 83% op + 11% exchange + 6% wait. So q18 is exchange-movement-bound, q19 is op-bound; coordination (wait) is NOT a target (§16.11).

**Prize (durable):** new `reprbench topk` mode A/Bs wide vs narrow `{order, rowRef}` in-state representation, recovering wide rows for the ≤k survivors only. **Row-narrowing captures 50% (q18) / 82% (q19) of the in-state op cost** — survivor fetch-back is cheap (narrow-raw ≈ narrow+fetch). Apportions ~evenly between kill-hash and shrink-key; narrow+fetch captures both (narrow key hashes cheap AND stores small). Control join-trace `idx` rows reproduce §21's 31–58% values.

**Decision: JUSTIFIED → build as next focused gated operator increment (q18 TOP-1 first).** This REFUTES §19's blanket "no cheap in-Step lever" — §19's reverted swap was a *container* change (dict→array, wide rows kept, regressed q9 +14%); row-narrowing is a *key-representation* change, 2–4× bigger, OUTSIDE the forbidden container zone. **Do NOT re-try the §19 container swap.**

**Why it's NOT a ThreadStatic seam (the catch):** capturing it needs (1) an order-key extractor threaded to the operator — already exists at both compile sites (`TypedPlanCompiler.BuildPartitionedTopK`'s `keys[i]`; `PlanToCircuit.CompilePartitionedTopK`'s order columns); add as an OPTIONAL builder/ctor param, reflection-safe because `BuildPartitionedTopK` is found by name then called as compiled code (no signature reflection — honors [[typed-compiler-reflection-gotcha]]); and (2) a wide-row recovery store (narrow key carries ref/index; typed value-struct path needs a backing buffer maintained under retraction; equal-order ties → small value-equality buckets). Plus snapshot compat, an equivalence PBT with the seam on, and a **q9 non-regression gate** (q9 shares this operator). Gate on q18 single-core `w1profile` + a W=8 step harness w/ per-tick output cross-check.

**§22.6 BUILT + SHIPPED (commit 70a4cf9, default-off seam):** `PartitionedTopKNarrowOp` keys `_accum`/`_window` by `readonly struct OrderRowKey {order value, wide row}` — hash on order value alone (kill-hash), wide-row compare only within an equal-order tie group, wide row carried IN the key (recovery store, no separate buffer/index). Behind `PartitionedTopKNarrowingMode` (ThreadStatic, Core, default-off), selected by `CircuitBuilder.PartitionedTopK` only for single-column ORDER BY. Both compile sites pass `keys[0]/descending[0]/nullsFirst[0]` when `SortKeys.Count==1` — reflection-safe exactly as predicted (`BuildPartitionedTopK` already had `keys` as a local; only its own call site changed). Snapshot byte-compatible.

**Correctness held:** `PartitionedTopKNarrowingPbtTests` (5000 iters, ±1 incl. retractions) — seam-on ≡ hand-written batch TOP-K oracle AND ≡ whole-row op; full suite green seam-off (1754 tests, byte-identical); W=8 gates cross-check identical output.

**Result INVERTS the q18-first framing — the load-bearing finding: the prize tracks per-partition STATE SIZE, not partition count.**
- **q19 (TOP-10, accumulating partitions): clean robust WIN** — W=1 −27% time / −55% alloc (deterministic), W=8 **1.30×/1.29×** step. The §22.2 83%-op-bound query meeting the §22.3 82% prize; §16.11 in-Step amplification carries it through Amdahl.
- **q18 (TOP-1, ~1 row/partition): measured FLAT** (W=8 parity/noise 0.89–1.08×, W=1 alloc **+2.3%**). Size-1 partitions → whole-row hash is CACHED (StructuralRow) + cheap (1-entry probe) → kill-hash prize ≈0, while the 16-byte struct key adds overhead. **Landmine 1(a)/1(b) materialised: `reprbench`'s VALUE-TYPE model over-priced q18's single-circuit/cached-hash reality.** This corrects §22.3's q18 optimism (not §19's pessimism this time).
- **q9 (shared op) UNHARMED:** alloc +0.2% flat — the §19 q9 regression does NOT recur.

Tooling shipped: `q18narrow [q18|q19]` (Q18NarrowBenchmark + `SpineParallelHarness.FlatNarrowTopK`), `w1profile … narrowtopk`, docs q18/q19-narrow-bench.md.

**§22.7 DEFAULT-ON via per-operator gate (this session):** the §22.6 "follow-on" — replaced the seam's SELECTION role with a per-operator compile decision; kept the ThreadStatic seam as a force override for the gates. `PartitionedTopKNarrowingMode.Enabled` (bool) → `.Override` (`Auto`/`ForceNarrow`/`ForceWholeRow`); selection in `ShouldNarrow(limit)` = `Auto` ⇒ `orderKey!=null && limit > AutoLimitThreshold(=1)`. Pure plan-read at both compile sites (no analysis, no reflected-signature change). Updated harnesses (SpineParallelHarness, W1ProfileBenchmark+`wholerowtopk` token, PBT) to force-arms.
- **Crossover sweep (`topkcrossover`/`TopKCrossoverBenchmark`, docs/topk-crossover-bench.md):** real single-circuit W=1 A/B of limit∈{1,2,3,5,10} on BOTH shapes. **LOAD-BEARING: `limit` is ORTHOGONAL to the prize.** Accumulating (q19) shape WINS at EVERY limit incl. 1 (limit=1 → 1.78×time/2.91×alloc, compressing to 1.48×/2.21× at 10). Tiny-partition (q18) shape pays a flat deterministic **+2.2% alloc at EVERY limit incl. 10**, time noise. Prize tracks per-partition ACCUMULATION; `limit` only correlated w/ the win across the 2 real queries by accident (q18=tiny+1, q19=accumulating+10).
- **Decision: flip default-on with `limit>1` — the right cut for the queries that exist + the only cheap static one.** Accumulation isn't compile-time-knowable. `limit>1` provably leaves ALL TOP-1 (q18/q9, both limit=1) BYTE-IDENTICAL (the +2.3% q18 regr cannot recur), routes q19→narrow. Caveat (documented landmine): off-diagonal mis-served — tiny k≥2 pays +2.2% no-win (no such Nexmark query), accumulating k=1 (q9's own op wins ~2.9× in isolation, join-diluted to +0.2%) left on whole-row = money on table. True predicate = RUNTIME per-partition state; runtime accumulation-adaptive gate is the named follow-on (out of scope for static plan-read).
- **Validation:** `PartitionedTopKSelectionTests` asserts operator type on BOTH compile paths (narrow limit∈{2,3,10}, whole-row limit=1 + multi-col ORDER BY; force-arms pin either). `w1profile` Auto vs `wholerowtopk`: q9 2345=2345B, q18 2173≈2175B byte-identical; q19 1734B/1742ns vs 3831B/2709ns (−55%/−36%) auto-captured. W=8 `q18narrow q19` 1.49×/1.69×. Full suite **1762 green** Auto default-on.
- **EXTERNALLY CONFIRMED vs Feldera (Run E, dbsp-bench-4.txt, [[nexmark-feldera-w14-snapshot]]):** q19 1c +34% (696K→935K/s), **10c 0.52→1.09× (LEAD), 14c 0.62→0.96×** — the narrow-key lever delivered competitively, not just same-box. Same pattern as the q4 §21 win (base throughput up × scaling). q18 stayed worst (0.38-0.64×, scaling-only improvement) — consistent with §22.8 NO-BUILD.

Do NOT re-try §19's container swap.

**§22.8 q18 shuffle-narrowing — MEASURED → NO-BUILD (measurement only, this session):** opened the prompt's gated follow-on (flow narrow {order,ref} through the SHUFFLE for q18's exchange-move share, §22.2/§22.5). Two measurements: (1) `stepprofile q18` re-decomp — **op DOMINATES (50-66% of step) and scales**, split+gather ("move") ~25-37%, wait small → re-confirms §15 (movement isn't the ceiling). (2) `gatherbench`/`ExchangeGatherBenchmark` (docs/exchange-gather-bench.md) — A/B per-worker split+gather wide-7col vs narrow {bidder,auction,order,ref} on the value-type uncached-hash model (typed W>1 path): gather-only −58%/−51%, **full split+gather −73%/−69%** (split IS width-attributable — typed exchange copies VALUE STRUCTS by value, not refs; corrected my first-pass assumption). Naive reach ~70%×~30%move ≈ ~20% step. **NO-BUILD because the two narrowable halves NEVER COEXIST for q18:** the microbench's narrow arm recovers wide rows from a pool pre-populated OUTSIDE the timed loop = assumes FREE recovery. Unwinding it: q18 is SELECT * (wide row needed at output, AFTER the shuffle, on the destination worker); the typed path (real movement, value structs) has NO heap identity → {order,ref} can't carry a free 8-byte ref → recovery needs BOXING (per-row alloc) or a shared id-pool whose maintenance reintroduces the wide-row cost; the structural W=1 path (free reference recovery, OrderRowKey §22.6) has NO movement to save (size-1, cached hash, already flat §22.6). Plus op floor (50-66%, the per-row TOP-K, flat to narrowing on size-1 per §22.6) is UNTOUCHED → ~20% step moves q18 ~0.44×→~0.53× vs Feldera, not parity. Residual = per-row op floor (§16.11/§17.5) + SELECT * wide-row materialization (§21.6 genuinely-wide residual). **§22 arc CLOSED: q19 default-on (§22.7), q18 NO-BUILD (§22.8).** Do NOT revive q18 shuffle-narrowing.
