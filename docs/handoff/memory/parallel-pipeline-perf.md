Work to close the gap vs Feldera on the parallel (W>1) Nexmark queries, esp. q4 (avg closing price — join + nested MAX/AVG aggregates) and q0 (passthrough). See [[feldera-comparison-benchmarks]] and [[roadmap-candidates]].

**Landed on main (June 2026):**
- Temporal comparisons in the typed expression compiler (`IsComparable` was missing Timestamp/Date32/Time64) — q4 wouldn't parallelize at all before this, because the typed pipeline is the *only* one with a parallel form; the BETWEEN filter fell back to structural/single-threaded.
- Partition-aware exchange elision: `TypedNode.PartitionKey` tracks the columns a stream is hash-partitioned by; an aggregate skips its exchange when the input is already partitioned by a subset of the group key (q4's join on a.id → GROUP BY (id,category)). ~17% on q4 step.
- Bucket-list exchange: the exchange gather buckets into plain lists, not ZSetBuilder dicts (input Z-set keys are already distinct, so a bucket never merges). ~13% on q4 step.
- ExchangeIndex fusion: fused the exchange gather with the downstream GroupProject re-index into one op (`ExchangeIndexOp`), so each full row is hashed once and the throwaway flat ZSet is never allocated. ~33% on q4 step, ~16% on q9. Wired into both join inputs + the aggregate's exchanged branch.

**Key soundness trap (why the obvious "narrow the shuffle" lever is blocked for q4):** column-pruning unused columns before an exchange is UNSOUND when a downstream aggregate is non-linear (MIN/MAX). Dropping columns collapses distinct rows with cancelling weights, erasing a value MAX depends on — the "unused" columns carry row identity. This is exactly why `PlanOptimizer.NarrowAggregateInput` bails on MIN/MAX. So q4's wide bid rows must shuffle full-width; the win had to come from the physical exchange, not logical pruning.

**Bottleneck profile (24-core box, 1M-event stream, W=14):** q0 is split(ingest-encode)+gather(egest-decode) bound, step≈0, already ~0.81× Feldera (little headroom — per-row VARCHAR transcode). q4 is step-bound; step scales only ~2× on 14 cores. Profile method: temporary `nexprofile` command timing split/step/gather (median of 9), A/B by `git stash`-ing the change. Benchmark cross-checks every W=14 output against W=1 ("ok" = verified).

**Per-tick overhead investigation (done, deflated the prize):** swept batch size + measured alloc/GC. Findings: (1) barriers are NOT the cost — W=1 (zero barriers) climbs ~18% with batch size too; (2) GC pauses are NOT the cost — only ~10 collections over a 1M-event run under Server GC; (3) the W=14 large-batch regression (50k→200k) is cache/bandwidth, not GC; (4) much of the small-batch penalty is re-emission amplification (a key touched in K ticks recomputes K times) — inherent to fine-grained incrementality, unfixable by engine changes. The system is CPU-bound (~1.2 GB/s alloc, not alloc-bound), dominated by whole-row hashing: Z-sets are `Dictionary<TRow, weight>`, so every join/aggregate/exchange hashes full row structs.

**Residual pushdown (DONE, d93db1d):** `JoinPlan.Residual` used to be dead code (resolver always null, both paths post-filtered). Now `PushFilterPastJoin` folds a cross-cutting WHERE conjunct above an INNER join into `Residual`, and the in-memory `IncrementalJoinOp` applies it during cross-product enumeration (rejected rows never enter the output Z-set — q4 no longer builds its ~920k-row join output, only the ~769k that pass BETWEEN). Spine join has no residual hook → post-filter fallback; structural already post-filters → unchanged. q4 step ~15% but within run-to-run noise (~18% even at median-of-9 cross-invocation — interleave or many iters for a clean number); provably less work though. The other scoped fusion (aggregate `(key,agg)→final` flatten) was NOT done — it changes a shared core operator's signature for an output-proportional (tiny) gain; skipped given the single-digit-% ceiling.

**q3 negative scaling (investigated June 2026, no fix — expected):** q3 (auction⋈person, both heavily filtered: category=10, state IN(...)) runs *slower* at W>1 than W=1 (~0.67–0.84× across runs). Root-caused, NOT a bug: (a) predicate pushdown is working — `PushFilterPastJoin` puts both filters below the join, so the exchange only shuffles filtered rows; (b) the join exchange partitions by the **extracted key** (a single bigint), not the whole row (`ExchangeIndexOp._partition` = hash(keyOf(row)); parallel join tests confirm correctness). The regression is just the fixed exchange + worker-grid coordination cost exceeding the parallel gain on a *tiny* filtered join (~16k rows split N ways → trivial per-worker work, everyone still pays shuffle/barrier). Confirmed batch-size-independent (single mega-batch still 0.75×), so it's per-shuffle overhead, not per-`Step`. No quick fix: a "don't-shard-small" guard needs cardinality stats the planner lacks, and q3 already beats Feldera 2.2–3.3× at every W. Real lever = the row-representation/exchange-cost work below. (q0/q1/q2 scale fine because pure map/filter needs only cheap round-robin input distribution, no key exchange.)

**q22 single-only FIXED (June 2026, commit 4f9d56d):** q22 (SPLIT_INDEX URL projection) was single-only at 0.22× Feldera *only* because SPLIT's `BuildTyped` returned null → structural fallback → no parallel plan (the parallel path is gated on the typed compiler). Added typed lowering for SPLIT_INDEX/SPLIT_PART → q22 now parallelizes (W=8 ≈ 3.15×). **General lesson: any structural-fallback scalar function forfeits the parallel plan for its whole query.** REPLACE/SUBSTRING/TRIM/POSITION/LIKE/REGEXP_* still return null from BuildTyped → queries using them are stuck single-only. Giving them typed lowerings is a standing source of parallel wins. See [[count-distinct-exact]] / [[scalar-function-registry-temporal]].

**q15/q16/q17 single-only FIXED (June 2026, commit 6c5b43c):** the per-day/per-channel statistics queries (`GROUP BY CAST(date_time AS DATE)` + `SUM(CASE…)` + `COUNT(DISTINCT…)`) were single-only for TWO independent reasons, both now fixed: (1) typed `CompileAggregate` bailed on any non-`ResolvedColumn` group key → generalized to lower arbitrary scalar group-key expressions into the key row (`BuildExprKeyExtractorDelegate`, mirrors the structural path); bare-column keys keep the fast path + exchange elision; the key exchange already shards on the extracted key so it works unchanged (guarded the partition build against unhashable key types). (2) **`AggregateKey` deduped its argument by RECORD equality**, which reference-compares a `ResolvedCaseWhen.Whens` / `ResolvedFunctionCall.Arguments` / `ResolvedInList.Values` list — so `SUM(CASE…)`/`COUNT(DISTINCT CASE…)` re-resolved at the 2nd collection site failed to dedup → aggregate collected TWICE. Structural tolerated the dup (flatten caps at plan.Schema); typed sized output to plan.Schema and the outer projection then read a column the aggregate never emitted → typed compile failed. Fix = structural `ResolvedExprEqual` (same shape as the [[group-by-expression-keys]] `AstEqual` gotcha, one layer down) + custom `AggregateKey` Equals/GetHashCode → dup collapses to one (both paths now compute once). Result: q16 ~1.9×, q17 ~2.7× at W=8, cross-checked W>1≡W1. q15 groups by day alone so speedup is bounded by distinct-day count (few-groups, like q3) — but no longer single-only. **General diagnostic lesson: a duplicate aggregate (dedup miss) shows up as a typed/parallel compile failure, NOT a wrong answer — structural masks it.** Bisect via TypedPlanCompiler.TryCompile on minimal queries + print AggregatePlan.Aggregates.Count.

**CORRECTION 2026-06-10 (see [[exchange-scaling-decomposition]]):** the "Bottleneck profile" claim above — that q4's step is bound by whole-row-hashing CPU / wide-row movement — was the *row-rep* lever (correct for the aggregate rebuild, fixed by the lazy view) but is **WRONG as the explanation for the W>1 SCALING ceiling.** The `stepprofile` step decomposition showed the all-to-all movement (split+gather, incl. whole-row hashing) is only 5–22% of the step and SHRINKS with W; the scaling ceiling is **barrier COORDINATION** (per-tick straggler wait, rising to 40% on q4 at W=24). Operators scale 7–9×, the realised step only 3.5–5×. So "narrow the shuffle" is not the lever; right-size W / coarser ticks / coalesce co-partitioned barriers are.

**Architecture followup (the real CPU lever — its own session):** row representation is the cost. Ranked: (1) dictionary-encoding / integer surrogate keys (intern rows → hash ints not structs; what Feldera/DBSP does) — biggest ROI; (2) shared arrangements (Differential Dataflow — indexed state built once, shared across operators, vs re-index every tick); (3) whole-query codegen (one IL routine, no per-row delegate dispatch, no intermediate Z-sets); (4) columnar/vectorized (near-rewrite); (5) typed ingest to kill `object?[]` boundary boxing. Followup should produce a design doc first, prototype only the top option behind a benchmark.
