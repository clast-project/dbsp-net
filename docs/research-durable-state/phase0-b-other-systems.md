# Phase 0-B: Incremental checkpoint and recovery in other systems (excluding Feldera)

Research brief for DbspNet's durable-state arc. Context: our state is in-memory mutable hash-indexed Z-sets. A checkpoint is a full O(state) rewrite as Arrow batches, and restore rebuilds the hash maps (CPU/boxing-bound; I/O is about 2.5%).

Confidence key: **[src]** means a cited page says it. **[recall]** means it comes from prior knowledge of these systems and was not re-verified this session. Treat [recall] items as leads, not facts.

---

## 1. Apache Flink

Flink has three generations of incremental durability. Each is worth studying because each one fixed the previous one's failure mode.

### 1a. RocksDB incremental checkpoints (Flink 1.3+)

- **Unit of durability.** The RocksDB SST file, an immutable sorted run.
- **Checkpoint without stopping.** On barrier the synchronous part flushes the memtable and takes a RocksDB native checkpoint, which is hard links to the current SSTs. The asynchronous part uploads only SSTs not already in DFS. Files uploaded earlier are referenced by placeholder handles. Processing resumes right after the synchronous part. [src] https://nightlies.apache.org/flink/flink-docs-stable/docs/ops/state/state_backends/ ; https://nightlies.apache.org/flink/flink-docs-stable/docs/ops/state/large_state_tuning/
- **Cost vs delta size.** Nominally proportional to the delta, but in practice proportional to **compaction output**. A compaction rewrites large files, which must then be uploaded. With many subtasks, some subtask is almost always compacting, so checkpoint duration is set by the slowest uploader and spikes unpredictably. The upload also cannot start until the barrier arrives. [src] https://flink.apache.org/2022/05/30/improving-speed-and-stability-of-checkpointing-with-generic-log-based-incremental-checkpoints/
- **Shared-file lifetime.** The JobManager's `SharedStateRegistry` reference-counts each shared SST by file-name key. When a checkpoint is subsumed (retention count exceeded), its references are decremented and files at zero are deleted. The FLIP-158 page warns that registry keys must depend only on the file name, not on backend UUID or key group, or sharing silently stops. [src] https://cwiki.apache.org/confluence/display/FLINK/FLIP-158%3A+Generalized+incremental+checkpoints . Getting this refcounting right took a long tail of bug fixes: placeholder double-registration, re-upload after delayed confirmation, and a regression where restored-checkpoint shared state was wrongly discarded (FLINK-24611 → FLINK-26985). [src] https://github.com/apache/flink/pull/21136/files ; https://github.com/apache/flink/pull/20722/files ; https://github.com/apache/incubator-flink/pull/39 . Flink 1.15 added snapshot ownership (FLIP-193, restore mode CLAIM / NO_CLAIM / LEGACY) because it was ambiguous who could delete the files of a checkpoint a job had been restored from. With NO_CLAIM, the first checkpoint after restore is a full one. [recall]
- **Recovery.** Download every SST of the checkpoint, multi-threaded, then open the DB. Cost is O(state) in bytes moved but cheap in CPU: there is no rebuild, because the SST is already the in-memory/on-disk format. Rescaling is worse. It opens several DBs and clips or copies key-group ranges; later releases sped this up with deleteRange and ingest-based restore [recall]. Docs: restore can be slower when network-bound, because more deltas must be fetched. [src] state_backends page. Task-local recovery keeps the native checkpoint directory on local disk, hard-linked to live files so it costs no extra space, and reuses it when the task is rescheduled onto the same slot. It is off by default, needs the same physical device as the live DB (FLINK-10954), and is lost if the TaskManager dies. [src] large_state_tuning page.
- **Hot vs cold.** RocksDB block cache and memtables in managed memory are hot. Local SSD holds the whole DB, so everything is local and DFS is backup only.
- **Lessons.** (a) "Incremental" in an LSM means incremental in **files**, and compaction converts small deltas into big uploads. (b) Distributed refcounting of shared files is a bug farm, and ownership semantics on restore must be explicit. (c) The web UI shows only the delta size, so users lose track of full state size. [src]

### 1b. Changelog state backend / generic log-based incremental checkpoints (FLIP-158, Flink 1.15+)

This is the most directly relevant design for a mutable-hash-map engine.

- **Unit of durability.** Two units. The first is the changelog segment in the DSTL (Durable Short-term Log): a DFS file batched per TaskManager, holding state-change records tagged with key group. The second is a periodic **materialization**, a normal snapshot of the underlying backend (heap or RocksDB). [src] FLIP-158
- **Checkpoint without stopping.** Every state write goes both to the live backend and to an in-memory changelog buffer, which is flushed to DFS continuously and on checkpoint. A checkpoint is acknowledged once the log entries up to that point are durable. The backend is **not** flushed. The checkpoint handle is the last materialization plus the changelog handles since then. Materialization runs in the background on a timer (default 10 min), at most one at a time, after which the log is truncated. [src] FLIP-158 ; 2022 blog
- **Cost.** At checkpoint time the cost is the size of the delta, which is the goal. Measured: p90 checkpoint duration fell from 6 s to 664 ms, and p99.9 from 10 s to 1 s. The costs are real. Full checkpoint size grew from 19.6 GB to 25.6 GB (and **45x larger** for sliding windows), recovery went from 20–21 s to **35–65 s**, and DFS I/O, serialization CPU, and TM buffer memory all rose. Hot keys updated many times between checkpoints make the log larger than a snapshot would be, because there is no squashing. [src] https://flink.apache.org/2022/05/30/improving-speed-and-stability-of-checkpointing-with-generic-log-based-incremental-checkpoints/
- **Shared-file lifetime.** Same `SharedStateRegistry` refcounting. The log is truncated after materialization, except for entries a pending (unconfirmed) checkpoint still needs. After a crash, orphan files are found by a scan of the checkpoint directory, which must finish before new checkpoints start. [src] FLIP-158
- **Recovery.** Restore the materialized snapshot, then **replay** the changelog, filtering by key group when rescaling. This is eager, and replay is CPU work proportional to log length. Hence the measured 2–3x slower recovery. [src]
- **Lessons.** (a) Decoupling the checkpoint from the snapshot moves cost from checkpoint latency to recovery time and space. Tune with the materialization interval. (b) Many tiny files at low data rates overload the coordinator, so batch across tasks per node. (c) DFS tail latency dominates, and request hedging cut p999 by about 47%. (d) Only one concurrent checkpoint; NO_CLAIM unsupported. [src] FLIP-158 ; state_backends page.

### 1c. FLIP-151: incremental snapshots of the heap (hash-map) backend

This is the closest analogue to DbspNet's representation.

- It uses the existing copy-on-write heap hash tables. Each entry gets a **version number bumped on write**, and each table remembers the last JM-confirmed version, so a snapshot writes only entries newer than that version. Removals go into a separate **removed-keys set**, not tombstones in the table, so the set can be dropped once confirmed. List and map state carry small journals (appended suffix, added and removed map keys). [src] https://cwiki.apache.org/confluence/display/FLINK/FLIP-151:+Incremental+snapshots+for+heap-based+state+backend
- Snapshots chain to earlier ones through `IncrementalStateHandle`, with **periodic full snapshots** (`checkpoint_id % N`) so old chains can be released. Recovery sorts the diffs by snapshot id and applies them in order. Any checkpoint failure falls back to a full snapshot. Keys must be immutable.
- Proof of concept: 1M keys × 10 KB, 10K updated per checkpoint. Checkpoint size fell from about 9.5 GB to about 114 MB (p75), and runtime from 12m22s to 9m21s. RocksDB incremental took about 18 min on the same workload.
- Advantages it claims over FLIP-158: squashes repeated updates to a key, holds only changed keys rather than a serialized log, and serializes once per checkpoint instead of on every access. Its drawback: no background materialization, so the chain must be compacted by periodic fulls. LSM-style merge-on-read was considered and rejected (more memory, slower reads). Status: "accepted" with a preview package; it never became mainline, and FLIP-158 is what shipped. [src]

### 1d. ForSt / disaggregated state (Flink 2.0)

- **Unit.** SST files stored **primarily on DFS/S3**, with local disk as a cache. ForSt is a RocksDB fork. [src] https://www.vldb.org/pvldb/vol18/p4846-mei.pdf ; state_backends page
- **Checkpoint.** The working files *are* the checkpoint files, shared zero-copy through a unified file-system view, so a checkpoint uploads almost nothing. Compaction can be offloaded to remote stateless workers (FLIP-430). [src] https://www.alibabacloud.com/blog/flink-state-management-a-journey-from-core-primitives-to-next-generation-incremental-computation_602503 ; https://cwiki.apache.org/confluence/display/FLINK/FLIP-430:+Remote+Compaction+For+Disaggregated+State
- **Recovery.** "Instant": open the DB pointing at remote files and do no download. Lazy, on-demand reads through a local cache. Reported in Alibaba's TMall case (290 GB state): recovery and rescale under 10 s (about 40x faster than 1.x), checkpoints 3–4 s regardless of state size. Vendor figures. [src] Alibaba blog
- **Price.** Remote reads are about 100x slower than local, so Flink 2.0 needed an **asynchronous state-access API (State API V2)** and an async execution model to hide latency. ForSt is still marked experimental (no canonical savepoints, no changelog). [src]
- **Lesson.** Lazy recovery requires that the on-disk format is the serving format, sorted and indexed, plus an execution model that tolerates cache misses.

## 2. Materialize (persist + differential dataflow arrangements)

- **Unit of durability.** A persist **shard** is a durable, definite time-varying collection of (k, v, t, diff). It is a trace of immutable **batches**, each with a `[lower, upper)` and `since` description. Each batch is split into **parts**, blobs in S3 with a target size of about 128 MiB per blob (`PersistConfig`). Shard metadata is a deterministic state machine in **Consensus**, a linearizable compare-and-set log (CockroachDB/Postgres) keyed by SeqNo. State changes are stored as **incremental diffs plus periodic rollups**, because rewriting full state on each change would be quadratic. [src] https://github.com/MaterializeInc/materialize/blob/main/doc/developer/design/20220330_persist.md ; https://dev.materialize.com/api/rust/mz_persist_client/struct.PersistConfig.html . Parts are now columnar (Arrow/Parquet-encoded "structured" data). [recall]
- **What is persisted.** Only **sources, tables, and materialized-view outputs**. **Intermediate arrangements (join and reduce state, indexes) are NOT persisted.** They live in the compute replica's memory as differential `Spine`s and are rebuilt on every restart. [src] https://materialize.com/docs/concepts/hydration/
- **Checkpoint without stopping.** The concept does not exist in compute. Durability happens upstream: each source or MV write is a batch appended through `compare_and_append`, advancing `upper`. Cost is proportional to the delta, by construction. Compaction is a separate, size-tiered process modeled on (forked from) differential's Spine. A spine batch can hold N hollow batches, so N-way merges reduce write amplification. "Fueling" merges in persist are only bookkeeping, and compaction never blocks writes. [src] https://dev.materialize.com/api/rust/mz_persist_client/internal/trace/index.html
- **Shared-file lifetime / GC.** Batches are written to writer-owned blob key prefixes and are write-once. A batch replaced by compaction is first **logically** deleted. It is **physically** deleted only after every reader's `seqno_since` has passed it and a newer rollup exists. Readers and writers hold **leases** in shard state, which avoids distributed-clock reasoning and lets GC reclaim from dead readers. Consensus history and old rollups are truncated the same way. [src] persist design doc
- **Recovery / rehydration.** A restarted replica re-runs every dataflow. Each `persist_source` reads a **snapshot** of its input shards at the `as_of`, then `listen`s, and all arrangements are rebuilt from scratch. This is **eager, and costs O(input state) of CPU and memory**. MV outputs are not recomputed (they are durable), but their operator state is, with a transient output buffer of up to 2x the output size. Sinks that recorded progress resume; otherwise they re-read the whole snapshot. Hydration is memory-heavy enough to cause OOM → restart → rehydrate loops on undersized replicas. [src] hydration docs
- **What they did about rehydration cost.** They did not persist arrangements. They worked around it:
  - **Active replication.** Multiple replicas per cluster, so one restart is invisible as long as another replica is up. [recall; docs]
  - **Zero-downtime (0dt) upgrades / blue-green.** The new version's clusters hydrate in **read-only mode** alongside the old ones before cutover. Hydration is hidden, not made cheap. [src] https://github.com/MaterializeInc/materialize/pull/34602 ; https://materialize.com/docs/manage/blue-green/
  - **Burst replicas.** `AUTO SCALING STRATEGY (ON HYDRATION)` adds a larger replica only while objects are un-hydrated. [src] hydration docs
  - **Memory engineering.** lgalloc, then **Linux swap**: about 30% faster hydration, about 3x memory headroom. This works because arrangements pack data into large contiguous regions (columnation). Dictionary compression halved peak memory without slowing hydration. [src] https://materialize.com/blog/scaling-beyond-memory/ ; https://materialize.com/blog/dictionary-compression-in-materialize/ ; https://materialize.com/changelog/2025-09-18-moving-to-swap/
  - Upsert-source state (latest value per key) can **spill to RocksDB/disk**. [src] hydration docs
- **Hot vs cold.** All arrangements are in memory (or swap); persist blobs sit in S3 behind an in-process blob cache. [recall]
- **Lessons.** (a) Persisting only inputs and outputs keeps durability cheap and simple, but makes restart cost O(state), and that is their biggest operational pain. (b) They chose to hide hydration (replicas, 0dt) over making it incremental. (c) Making rebuild memory-efficient (contiguous, columnar, swap-friendly) paid off more than raw I/O work. That matches our finding that restore is CPU/boxing-bound.

### Differential Dataflow's own persistence

- DD's arrangement is a `Spine` of **immutable sorted batches**, merged geometrically. A new batch is sealed on every frontier advance. That makes it naturally checkpointable: a batch is a write-once file, and a trace is a list of batch references. [src] https://docs.rs/crate/differential-dataflow/latest/source/src/operators/arrange/mod.rs
- Materialize's **first** persistence crate (2021, `persist`) described a "persisted arrangement structured to allow indexed access", so durable arrangements were the original intent. It was replaced by the current shard design, which persists only collections, not compute arrangements. [src] https://dev.materialize.com/api/rust/persist/index.html . Why they dropped persisted compute arrangements (my reading, [recall]): arrangement contents are worker- and partition-specific and change with plan or version upgrades, so they are not a stable durable artifact.

## 3. RisingWave Hummock

- **Unit of durability.** The **SST** (about 64 KB data blocks, plus a meta file with index and bloom filter) on S3-compatible object storage. Every key carries an **epoch**. A Hummock **version** is the set of SSTs plus `max_committed_epoch`, managed by the meta node. [src] https://risingwavelabs.github.io/risingwave/design/state-store-overview.html
- **Checkpoint without stopping.** Meta injects barriers carrying epochs (barrier interval about 1 s; checkpoint every N barriers; effective default sources cite 1–10 s). On barrier, operators move their dirty per-epoch local state into the per-node **shared buffer** and continue immediately. A background task builds SSTs, merging many tables per epoch into few SSTs, which cut "hundreds of SSTs per epoch" overloading meta. It uploads them to S3 and registers them. A checkpoint is complete only when every operator's epoch data is uploaded and committed in meta. Reads merge local state, then the shared buffer, then the committed store. Cost is **proportional to the epoch's delta**, because the LSM is natively incremental. Compaction runs on separate **compactor nodes**, which can be spot instances. [src] https://risingwavelabs.github.io/risingwave/design/shared-buffer.html ; https://www.risingwave.com/blog/state-management-for-cloud-native-streaming-getting-to-the-core
- **Shared-file lifetime / GC.** Readers pin versions and epochs. Compaction produces new versions, and files referenced by no pinned version are deleted by a background **vacuum**. Compaction keeps a key-value pair only if it is the latest version or its epoch is above the low watermark. Meta backups snapshot only metadata, not SSTs, and two clusters must never share one SST set. [src] state-store-overview ; https://docs.risingwave.com/operate/meta-backup . There is also a "full GC" that lists the object store for orphans left by failed uploads. [recall]
- **Recovery.** Meta rolls back to the last committed epoch, rebuilds the actor graph, and sources rewind to offsets stored in state. **No state download and no rebuild.** Operators read through to S3 lazily, so recovery is roughly constant time (vendor claim: 10–20 s regardless of state size, vs 900+ s for Flink RocksDB at 10 TB; marketing, not measured). Replay is bounded by the checkpoint interval. [src] https://risingwave.com/blog/apache-flink-recovery-time-vs-risingwave-benchmark/ ; https://risingwave.com/blog/architecture-distributed-streaming-database/
- **Hot vs cold.** Tiers: operator in-memory cache (e.g. join-side hash cache, fully in memory for tiny states like SimpleAgg), block cache and meta cache in memory, an optional **local-disk hybrid cache** (Foyer: memory plus disk; about 90% data / 10% meta), and S3. **Cache refill after compaction** prefetches the new blocks of recently used data before the new version is applied, because compaction otherwise invalidates the cache. The disk cache starts **cold after restart** by default; an option tries to reload it, and refilling levels can lengthen recovery. [src] https://docs.risingwave.com/deploy/disk-cache ; https://docs.risingwave.com/docs/1.10/node-specific-configurations ; https://risingwave.com/blog/the-case-for-hybrid-cache-for-object-stores/
- **Lessons.** (a) Time to first output is fast, but **latency after recovery is poor** until caches warm. Cold-key lookups (joins, TopN) go remote and are expensive. (b) Compaction destroys cache locality, hence refill. (c) Per-epoch small files overload the metadata service; the fix was batching at node level. (d) Endless-recovery loops from OOM or network problems are a known failure mode. [src] https://docs.risingwave.com/troubleshoot/troubleshoot-recovery-failure

## 4. Brief: Kafka Streams, Arroyo

**Kafka Streams.** The unit is a local RocksDB store plus a **compacted changelog topic** per store. Every write is also produced to the changelog, so this is a delta log by construction. On commit, the producer is flushed and changelog offsets are recorded in a local `.checkpoint` file (since KIP-1035, inside the store itself). Cost is proportional to writes, with no squashing within a commit except through the record cache. Recovery: if local state survived, replay only the changelog tail from the checkpointed offset; if not, replay the **whole** compacted topic. That is eager and O(state), and slow, which is the classic pain. Under exactly-once a hard crash historically wiped local state and forced full restore; KIP-892 (transactional state stores) addresses this [recall]. Mitigations: **standby replicas** continuously tail the changelog (a hot copy, helpful mostly for crash failover), and KIP-441 **warmup replicas** restore in the background before handover, with the old owner staying active until the new one has caught up. Topic compaction is the GC. [src] https://www.conduktor.io/kafka-streams/state-restore ; https://kafka-options-explorer.conduktor.io/kip/441/ ; https://docs.confluent.io/platform/current/streams/developer-guide/running-app.md

**Arroyo.** Barrier-epoch checkpoints write per-operator, per-subtask table files (originally Parquet) to S3 under `{job}/checkpoints/checkpoint-{epoch}/operator-{id}/table-{name}-{subtask}`. Tables have their own compaction and expiration, for example time-keyed tables expire by watermark. Known pitfall: a flusher panic on an S3 error stalled checkpointing (issue #444). Detail is thin. [src] https://deepwiki.com/ArroyoSystems/arroyo/4-storage-and-state-management ; https://github.com/ArroyoSystems/arroyo/issues/444

## 6. Implications for a design whose in-memory state is a mutable hash map

**Approaches that work without changing the in-memory representation**

1. **Delta log + periodic base (FLIP-158 style).** DBSP gives us the log for free. Every stateful operator's per-tick input delta (or the delta it integrates into its trace) is already a Z-set. Appending each tick's integrated deltas to a log is O(delta), and the checkpoint is "log durable up to tick T". Rewrite the full base (our current Arrow checkpoint) in the background at a materialization interval, then truncate. Costs, as Flink measured: recovery = base restore + replay, which for us means hash-map inserts and is exactly our CPU-bound path. Expect recovery to get slower in proportion to log length, and space to grow. Hot keys inflate the log unless deltas are consolidated per checkpoint interval. Z-set addition makes consolidation natural and cheap: sum the deltas of N ticks into one Z-set before writing, which squashes repeats and cancels +1/−1.
2. **Dirty-tracking diff snapshots (FLIP-151 style).** Track the keys touched since the last confirmed checkpoint (a version stamp per entry, or a per-operator dirty-key set), and write only their **current weights**, with weight 0 meaning removed. This squashes better than a log. With DBSP weights the diff can literally be "current − previous" as a Z-set, so no separate removed-keys set is needed: emit the negated old weight. It needs a chain of diffs with periodic fulls to bound recovery. Recovery is still an eager rebuild.
3. **Hide recovery instead of speeding it (Materialize / Kafka Streams).** Standby or warm replicas, or blue-green pre-hydration, need no format change and fix availability but not cost. Materialize's experience also says that making rebuild memory- and CPU-efficient (contiguous, columnar, unboxed) beats I/O work. That matches our finding that restore is about 97% CPU.

All three keep **recovery eager, O(state) of CPU**. They fix *checkpoint* cost (O(state) → O(delta)) but not *time to first output*.

**Approaches that require sorted immutable runs**

4. **Shared-file incremental (Flink RocksDB, Hummock, persist, DD Spine).** Durable units are write-once sorted runs, a checkpoint is a manifest of run references, and GC refcounts or pins runs across retained checkpoints. This needs the in-memory or on-disk trace to *be* a set of immutable runs (our spine path, not the flat hash path). Lesson from Flink: compaction turns small deltas into large uploads unless merged runs are deduplicated by content or kept local. Lesson from everyone: shared-file refcounting and ownership is where the bugs live. Prefer a single owner with lease- or epoch-based physical deletion (persist, Hummock) over distributed refcounts.
5. **Lazy / instant recovery (ForSt, Hummock).** This requires the durable format to be the **serving** format: sorted, block-indexed, bloom-filtered, readable without a full rebuild. It also needs an execution model that tolerates cache misses (Flink had to add async state access) and a cache-warming strategy (RisingWave refill). With a mutable hash map as the serving structure there is no lazy path: a hash map must be fully built before the first lookup is correct. This is the same conclusion our lazy-restore arc reached (an LSM-style storage change).

**Suggested sequencing for DbspNet.** Ship (1) or (2), using Z-set deltas, consolidated per checkpoint interval, with a background base rewrite. This turns checkpoint cost from O(state) to O(delta) with no representation change, and is closest to FLIP-158 plus FLIP-151's squashing. Keep checkpoint metadata as a manifest of immutable files from day one: base files and delta files, single-owner GC by "oldest retained checkpoint" (persist-style logical-then-physical delete). Swapping base files for sorted runs later (option 4/5) then changes only the file kind, not the protocol. Budget for recovery getting slower by the replay length, and bound it with the materialization interval.
